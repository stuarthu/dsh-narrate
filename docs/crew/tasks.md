## 读这张表之前要知道的四条规则

1. **两个任务绝不拥有同一个文件。** 工程师同时开工，共用文件会互相覆盖。
2. **`T-01` 是走通骨架，已完成。** 后面的任务**不准再改它拥有的文件**，只有一处例外，写在 `T-10` 那一行。
3. **测试命令只有一条。** `T-01` 在 `package.json` 的 `test` 脚本里定下了，之后每个任务都用同一条 `npm test`，不准自己另起一套。
4. **每个代码任务都是测试先行。** 先写一个失败的测试，确认它是因为功能缺失而失败，再写最小的代码让它通过。报告里必须有失败的那次输出，再有通过的那次。没有失败输出的报告不算完成。

## 我认为还弱的地方

1. **`T-06` 挑素材的质量没法用自动测试保证。** 测试只能证明"能配上的配上了、配不上的报出来、时长过滤生效、画面搜索缺失时会退回"，不能证明"配得好看"。这一条只能靠停点 3 由用户判断。
2. **分配的四个数字是真实素材上调出来的，不是想出来的**：降权 1.5、相邻额外减 3、缺素材门槛取全篇中位数的 0.5、换花样只在最高分 80% 以内的候选之间做。最后那一条是必须的——不设它，海浪用过之后"下次去看看海"会被推到一段完全不相关的素材上。想再调就改 `DEFAULTS`，四个都是可调参数。
3. **英文查询要写主体，不要写拍摄手法。** `time lapse`、`slow motion`、`drone shot` 会匹配上任何同手法拍的素材，把主体词压下去。实测：`bright sky with moving clouds, time lapse` 配上了一段工业烟雾的延时；改成 `clouds bright sky` 就对了。这条要写进将来那个"做画面对应表"的工具的 `description` 里——agent 只看得到那里。
4. **`Q-6` 已定**：缺口 ≤ 20% 放慢，> 20% 循环。归 `T-09` 实现，要动 `T-01` 的 `segment.js`，理由写在 `T-09` 那一行。
5. **字幕这一条原来的诊断是错的，`T-09` 做的时候量出来了。** 原来写的是"字幕必须在缩放之后再烧，因为 `FontSize`/`MarginV` 是绝对像素"。先缩放再烧是对的，也照做了，**但它救不了这个问题**：`force_style` 里的数字根本不是像素——libass 会按 `画面高 / 脚本高` 缩放它们，而脚本高默认是 288。实测 1080 高时 `MarginV=60` 画成离底 248px，1920 高时 `MarginV=220` 画成离底 **1525px**，字幕跑到画面顶部，而当时每个单元测试都是绿的。真正的改法是自己写 `.ass` 并钉住 `PlayResX/PlayResY`，样式值再从写死的像素改成比例。经验：**"绝对像素"这种量，一定要在真画面上量一次再信。**
6. **PRD 的 `Q-5` 现在只卡第 3 层漏斗。** 画面搜索需要那 2 GB 的向量层。不装也能跑，只是挑素材靠文字，质量差一些。这已经不再是一个阻塞问题，而是一个质量选项——契约版本 4 把它设计成了可退回的。
7. **`A-11` 里"画面上的字确实是那几个字"没法完全自动测。** 自动测试能证明画的是真字形不是方块（笔画多的字墨量明显多于笔画少的字），也能证明字幕文件内容和文稿一致。但"渲染出来的像素就是这几个字"要人眼看。这一条靠里程碑评审兜。
8. **默认语音引擎会联网，把旁白文字发给微软。** 已在 `README.md` 和 `README-zh.md` 的隐私一节披露，`T-10` 更新 README 时不许删掉那一节。
9. **跨语言匹配只能靠 agent 给的英文查询。** 中文文稿对英文素材元数据，字符二元组的交集是空的——36 段真实素材上实测每一段都是 0 分。所以英文查询在实践中几乎是必需的，不只是第 3 层的可选项。已写进契约版本 11。原来这一条写的是"文字层必须按稀有度加权"，那一条已经做完了：`fair use` 权重 0.000，`fire` 2.225。 真实素材证明了这一点：从 archive.org 下载的素材每个带 20 到 32 个标签，大半是 `HD`、`1920x1080`、`H.264`、`Fair Use` 这类**每个素材都有**的格式噪音，真正有用的 `forest`、`mountain` 被淹在里面。一个所有素材都有的标签携带零信息量。不加权的话第二层漏斗基本白做。
8. **下载来源的标题常带格式尾巴**（`Mountain Fog (Free to Use HD Stock Video Footage)`）。去掉要靠猜规律，所以不做。模型读到它不会理解错，只是稍微啰嗦。
11. **横屏素材做竖屏成片时，上下会有很大的黑边。** 加黑边保住了比例、不拉伸，这是诚实的做法，但抖音和 Shorts 上常见的做法是裁到满屏或者背景虚化填充。这是一个产品选择，不在 `T-09` 范围内，也没有测试假装它已经解决了。要改就是一个新的变更请求。
12. **拼接的验收要"完整解码一遍"，长片子会慢。** 一条十分钟的 1080p 成片解码一遍大概几十秒。值得：拷流拼坏的时候 ffmpeg **退出码是 0**，只量时长看不出来（实测一次只差 0.02 秒，但帧数少了四分之一）。宁可慢，不能交坏片子。
13. **中文文件名不分词。** `服务器机柜-特写` 能切出三个词，`服务器机柜特写` 只算一个。`T-03` 的文件名读取器只能做到这个程度，不要指望它。
