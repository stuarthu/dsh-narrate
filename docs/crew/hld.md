## 1. 在建什么

一个 dsh 插件。它按顺序跑五个阶段，中间在四个地方停下来等用户回答。每个阶段读上一个阶段写的文件，写自己的文件。阶段之间不互相调用。

## 2. 复用了什么，什么是新的

**先找现成的，再考虑自己写。** 这个项目最重要的设计决定就是尽量不写。

| 用到的东西 | 来源 | 干什么 |
| --- | --- | --- |
| `dsh-video-understand` | 别人的 dsh 插件 | 把一段视频在本地变成文字（语音识别 + 场景 + 运动） |
| `dsh-ffmpeg` | 别人的 dsh 插件 | `probe` 探时长、`cut` 裁片段、`concat` 拼接、`subtitle` 烧字幕、`encode` 转码 |
| `ffmpeg` 直接调用 | 系统命令 | 补 `dsh-ffmpeg` 没有的两件事：把旁白混进视频、把素材拉长到指定时长 |
| 外部语音命令 | 用户配置 | 文本进、音频出。自带一个免费默认 |

| 新写的模块 | 为什么必须新写 |
| --- | --- |
| `flow` | 四个停点的流程和续跑，没有现成的。这是本项目唯一真正独特的部分 |
| `assets-index` | 现成插件能理解**一个**视频，但没有"管理一个文件夹、只算变化的、保留手改"这一层 |
| `script` | 现成工具直接写稿，不先反问用户。停点 1 是新的 |
| `shotplan` | 现成工具自动配画面且不停下来。"缺素材要报给用户"是新的 |
| `voice` | 引擎是别人的，但"一句一个文件 + 报真实时长 + 引擎可换"这层包装是新的 |
| `render` | 拼装逻辑是新的：画面时长服从音频、分批拼接、横竖屏字幕规则 |

## 3. 模块

| 模块 | 一句话职责 |
| --- | --- |
| `flow` | 决定下一步跑哪个阶段、在四个停点停住、管工作状态、把工具挂到 dsh 上 |
| `assets-index` | 扫素材文件夹，为每段素材在它旁边写一个 JSON：把你的输入翻译进 `fromYou`，把机器算的按时间段写进 `fromMachine`。只算指纹变了的 |
| `script` | 停点 1 反问用户；停点 2 把想法展开成按句编号的文稿 |
| `shotplan` | 为每句挑一段素材：三层漏斗筛候选（时长 → 文字 → 画面搜索），然后统一分配（用过的降权），写出画面对应表，把挑不到的句子列成缺素材报告 |
| `voice` | 为每句生成一个音频文件，量出它的真实时长，引擎可换 |
| `render` | 按对应表裁素材、把画面时长对齐音频、混音、烧字幕、分批拼接、转码出片 |

## 4. 边界在哪里，为什么在那里

**核心决定：模块之间用文件说话，不用函数调用。**

系统最终会长成建造它的人的沟通形状。造这个系统的工程师之间**完全不能说话**。所以任何两个模块必须先约定的东西，都要写成文件格式，否则根本不会被约定。

文件传递还带来两个实际好处。第一，任何一步不满意，改那一个文件重跑下一步就行，不用整条重来。第二，用户能亲眼看到每一步的产物，而这正是四个停点存在的意义。

一共三条边界：

| 边界 | 契约文件 | 谁写谁读 |
| --- | --- | --- |
| 工作文件 | `docs/crew/api/flow-stages.md` | `flow` 拥有格式，并写 `meta` 和 `idea` 两节；五个阶段各写自己那一节 |
| clip 描述文件（一个 clip 一个 JSON） | `docs/crew/api/assetsindex-shotplan.md` | `assets-index` 写，`shotplan` 读 |
| 语音引擎 | `docs/crew/api/voice-engine.md` | `voice` 调用，外部引擎实现 |

**为什么工作文件只有一个，而不是每个阶段一个。** 每个阶段独占自己的一节，没有两个阶段写同一节。一个文件比五个文件少四份格式约定，两个不能说话的工程师要读的东西少了四份。

## 4.1 谁是编排者：agent，不是宿主

**宿主不能调模型。** dsh 插件的形状是 `apply(ctx, config)` 加 `ctx.tools.register(定义)`，
工具的 `execute` 在宿主进程里跑，把返回值交给 agent。宿主这一侧没有任何调模型的入口。

所以三件需要模型的事——写文稿、补问额外问题、理解素材——都不能做成"宿主调模型"的
函数。真实形状是反过来的：

| 事情 | 谁做 |
| --- | --- |
| 记住规则、校验、编号、存盘、说"下一步该干什么" | **插件**（宿主侧） |
| 写文稿、补问、调 `video_understand` | **agent**（模型侧） |
| 决定次序、在停点上跟用户说话 | **agent**，按插件给的次序说明走 |

这条约束反过来把职责分得更干净了：**插件是规则和记忆，agent 是判断力。** 插件里
没有一行代码需要"聪明"，所以每一行都能写确定的测试——现在那 138 个测试就是这么来的。

代价是**编排不在宿主里**。插件不能强迫 agent 按顺序走，只能在每个工具里检查前置
条件，不满足就报错。所以每一个"不能跳过"的规则都必须是工具自己的硬检查，不能只
写在说明里。停点 1 的 `E_INTERVIEW_INCOMPLETE` 就是这个道理。

## 5. 数据怎么流动

```
用户的一句想法
      │
      ▼
  ┌────────┐  停点 1：反问
  │ script │  停点 2：审文稿
  └────────┘
      │ 工作文件的 script 节（按句编号的文稿）
      ▼
 ┌──────────┐ ◄─ 每个 clip 一个 JSON ─ ┌──────────────┐
 │ shotplan │                      │ assets-index │
 └──────────┘   停点 3：审对应表   └──────────────┘
      │ 工作文件的 shotplan 节                │
      │                                       └── dsh-video-understand
      ▼
  ┌───────┐  停点 4：只听声音
  │ voice │
  └───────┘
      │ 工作文件的 voice 节（每句的音频路径和真实时长）
      ▼
  ┌────────┐
  │ render │ ── dsh-ffmpeg + 直接调 ffmpeg
  └────────┘
      │
      ▼
   成片 mp4
```

`assets-index` 不在这条链上。它跟着素材文件夹走，一次入库能给很多个视频用。

## 6. 最危险的边界

**`voice` 和 `render` 之间**，也就是工作文件的 `voice` 节。

三个理由：

1. **画面时长由音频决定，而音频时长只有跑完才知道。** 别的地方都是"先想好再做"，这里是"做完才知道"。如果 `voice` 报的时长和 `render` 理解的时长有一点不一致（比如一个含静音尾巴、一个不含），成片就会越往后越不同步。
2. **`dsh-ffmpeg` 在这里缺工具。** 它没有"把旁白音频混进视频"的工具，也没有"把素材拉长到指定时长"的工具。这两件事必须自己直接调 `ffmpeg`，而这是本项目唯一要绕过现成插件的地方。
3. **它是唯一一条会被后面每一句话重复走过的路。** 错一次，错一百次。

所以 `T-01` 是走通骨架，跨的就是这条边界：一句文本 → 一个音频 → 一段裁好的画面 → 一句烧上去的字幕 → 一个真能播的 `mp4`。一个工程师同时拿两边的文件。别的任务都等它。

## 7. 故意不做的事

| 不做 | 原因 |
| --- | --- |
| 阶段之间用函数调用或消息队列 | 文件足够，而且用户看得见 |
| 把描述放进数据库 | 一个 clip 一个小 JSON 就够。而且文件放在 clip 旁边，拷素材时描述一起走，数据库做不到这件事 |
| 把语音引擎写成代码插件 | 命令行契约让任何语言写的引擎都能接，见 `adr/0003` |
| 自己实现视频理解或视频编码 | 见第 2 节 |
| 并行跑多个阶段 | 阶段之间严格前后依赖，并行没有意义 |
