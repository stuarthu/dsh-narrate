# 边界契约：素材索引文件（`assets-index` → `shotplan`）

| 项目 | 值 |
| --- | --- |
| 版本 | 1 |
| 拥有者 | `assets-index` |
| 涉及任务 | `T-02`（索引读写和保留手改）、`T-03`（接视频理解）、`T-05`（`shotplan` 读它） |

## 风格

**文件交接。** 一个 JSON 文件，路径 `<素材文件夹>/.narrate-index.json`。

它放在素材文件夹里，**不放在工作目录里**。理由：一次入库要给很多条视频用。索引跟着素材走，不跟着某一条视频走。

## 格式

```json
{
  "schema": 1,
  "assets": [
    {
      "path": "/home/you/assets/bench.mp4",
      "fingerprint": "size:104857600|mtime:1755600000",
      "durationSec": 63.200,
      "description": "服务器机柜特写，有人在插网线，机房蓝色光",
      "tags": ["服务器", "机房", "特写"],
      "describedBy": "auto",
      "confidence": "low",
      "stale": false,
      "engine": "video-understand-l0"
    }
  ]
}
```

## 字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `path` | string | 是 | 素材绝对路径。同一个 `path` 只能有一条记录 |
| `fingerprint` | string | 是 | 用来判断文件变没变。形状 `size:<字节>\|mtime:<秒>` |
| `durationSec` | number | 是 | 素材总长，秒，3 位小数 |
| `description` | string | 是 | 画面里有什么，一到三句话 |
| `tags` | string[] | 是 | 关键词。可以是空数组，但字段必须在 |
| `describedBy` | `"auto"` 或 `"human"` | 是 | `auto` = 机器写的；`human` = 人改过的 |
| `confidence` | `"high"` 或 `"low"` | 是 | 机器对这条描述有多大把握。人改过的一律 `high` |
| `stale` | boolean | 是 | 文件变了但描述还没更新 |
| `engine` | string | 是 | 哪个引擎写的，例如 `video-understand-l0` |

## 数据归谁，读的人可以相信什么

- **`assets-index` 拥有这个文件。`shotplan` 只读，一个字都不能写。**
- 索引里有的素材，**不保证现在还在磁盘上**。用户可能删了文件却没重扫。`shotplan` 挑中一段素材后必须自己确认文件存在，不存在就报 `E_ASSET_MISSING`。
- `confidence` 是 `low` 的记录，描述可能很空。`shotplan` **必须**把 `low` 的记录当成较弱的证据：只有在没有 `high` 记录能配上这句话的时候才用它，而且用了要在缺素材报告里提一句"这句配的是把握不高的素材"。
- 这条规则是为了应对一个真实的限制：本地视频理解靠语音识别、场景切换和运动，一段**没有人说话**的画面，它几乎说不出内容。

## 规则：人的修改绝不能被机器盖掉

这是本契约最重要的一条。

| 情况 | `assets-index` 必须怎么做 |
| --- | --- |
| 新文件 | 理解它，写一条 `describedBy: "auto"` 的记录 |
| 文件没变（指纹相同） | **什么都不做。** 不重新理解，不花钱 |
| 文件变了，`describedBy` 是 `auto` | 重新理解，覆盖描述，更新指纹 |
| 文件变了，`describedBy` 是 `human` | **保留人写的描述**，把 `stale` 设成 `true`，更新指纹，并在报告里列出这条让用户自己决定 |
| 索引里有、磁盘上没有 | 保留记录，`stale` 设成 `true`，在报告里列出。**不准删记录** |

不准删记录的理由：用户可能只是把素材挪到了外部硬盘上。删掉描述就等于把他手写的东西扔了。

## 错误名字

| 错误名 | 什么时候 |
| --- | --- |
| `E_INDEX_UNREADABLE` | 索引文件存在但不是合法 JSON。不准覆盖它，报错停下 |
| `E_INDEX_SCHEMA_UNKNOWN` | `schema` 不是本模块认识的版本 |
| `E_ASSET_UNREADABLE` | 素材文件存在但读不出时长 |
| `E_ASSET_MISSING` | 索引里写的路径在磁盘上不存在 |
| `E_UNDERSTAND_FAILED` | 视频理解失败。这一条跳过并记下，**不中断整次入库** |
| `E_DUPLICATE_PATH` | 索引里同一个 `path` 出现两次 |

## 好不好用

读的人最容易犯的错，是把 `confidence: "low"` 当成和 `high` 一样可信，然后配出一堆错画面。防住它的办法：读索引的接口不返回一个大列表，而是分两个——`highConfidence()` 和 `lowConfidence()`。想用弱证据，必须显式去要。

## 契约测试

| 侧 | 测试证明什么 |
| --- | --- |
| `assets-index` 侧 | 建 3 个假素材，入库；手改第 2 条描述并把 `describedBy` 改成 `human`；碰一下第 2 个文件的修改时间；再入库。测试证明：第 1、3 条没被重新理解（调用次数为 0），第 2 条的人写描述**还在**，且 `stale` 变成 `true` |
| `shotplan` 侧 | 手写一个索引桩，里面 1 条 `high`、1 条 `low`。测试证明：能配上 `high` 的句子用了 `high`；只能配上 `low` 的句子用了 `low` 且在缺素材报告里带上了"把握不高"的说明。**必须跑在手写桩上，不准调真的 `assets-index`** |

两个测试都必须先失败再通过。

## 改这个文件的规矩

契约在任何一侧的任务开工之后就**冻结**。工程师发现它错了，报给 PM，PM 交给架构师。**只有架构师能改这个文件。** 改完 PM 通知两侧重读新版本。

必须改的时候，优先**只加不改**：加一个新字段、且不设为必填。这四种改法会弄坏另一侧，做了就要说清楚，而且两侧都要重跑：改字段名、删字段、把可选字段变必填、改一个错误名的含义。
